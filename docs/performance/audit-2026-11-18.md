# Performance audit, 18 November 2026

Measured on a church-sized library: 4,500 bilingual hymns (English and Fante, six verses
each) and a 32,000-verse Bible, release builds, many runs per operation (median and worst).
Benchmarks are in the repository, so the audit can be repeated:

    cargo run --release -p wp-core --example perf      # library, scripture, recognition, NDI
    cargo run --release -p wp-render --example perf    # built-in NDI renderer

## Results

| Operation | Median | Worst |
| --- | --- | --- |
| Go live with a song (load and build slides) | 0.05 ms | 0.13 ms |
| Open a chapter by reference (John 3:16) | 0.11 ms | 0.28 ms |
| Quick hymn number ("555") | 0.57 ms | 0.83 ms |
| Follow the preacher (one sentence) | 0.36 ms | 0.46 ms |
| Sermon outline to slides | 0.61 ms | 2.2 ms |
| Song search, one word | 8.2 ms | 17 ms |
| Song search, three words | 10 ms | 15 ms |
| Song list, all 4,500 (Songs tab) | 54 ms | 68 ms |
| Bible word search (after its index exists) | 11–24 ms | 36 ms |
| Bible word index, built once per Bible | 241 ms | |
| Verse read aloud, per Bible checked | 62 ms | 97 ms |
| NDI: one 1080p frame to UYVA | 5.8 ms | 14 ms |

Interface: 560 KB of code (173 KB compressed), plus the PDF reader (350 KB) loaded only
when a PDF is imported. Library file: 48 MB for the test library.

## Fixed in this audit

1. **Built-in NDI renderer.** Each text layer was processed as a whole 1920×1080 frame
   (mask, shadow blur, outline, painting) though the words fill a small part of it. It now
   works only on the area around the words. The pictures are unchanged (the renderer's
   pixel tests pass).

   | Theme | Before | After |
   | --- | --- | --- |
   | Stream lower third | 172 ms | 19 ms |
   | Methodist hymn, bilingual | 131 ms | 37 ms |
   | Hymn, white box | 69 ms | 17 ms |
   | Scripture reference bar | 174 ms | 45 ms |

2. **Recognising a verse read aloud** searched every Bible when no reading was live: about
   1.2–2 s every 3 s with 20 Bibles, holding the library (the rest of the app waited). It
   now searches the live reading's Bibles, else the first English Bible, whose word index
   is prepared when listening starts (no 0.24 s-per-Bible stall at the first check).

3. **Transcript polling** sent up to 300 transcript lines with every status request (up to
   five a second with the Transcript panel open). Lines are now sent only when new ones
   have been said; the window keeps its copy.

## Noted, not changed

- The service window makes about 5–6 small background requests a second when idle
  (output status 0.4 s, speech and notes 0.7 s, recording 1 s). Fine as it is; they could
  be combined into one.
- NDI frame conversion takes about 17 % of one core while sending 30 frames a second.
  Acceptable; it could use SIMD if it ever matters.
- Every projector window loads the whole interface code. A smaller output bundle would
  make projector windows start a little faster.
- The song list builds all 4,500 rows at once (54 ms in the library, more to draw).
  Fine today; a virtual list would help with much larger libraries.

## Follow-up (20 Nov 2026)

- The four regular status requests of the service window (outputs every 0.4 s, speech
  0.7 s, recording 1 s, pulpit notes) are one request now (`status_all`); calls within
  0.25 s share its answer.
- Projector, stage and NDI windows load about 215 KB instead of 575 KB: the operator
  interface and the browser preview's stand-in (`api.mock.ts`) load only where needed.
- Found while doing this: the speech status sent "-1" for "no transcript lines yet",
  which the app refused, so in the real app the speech status (and the Transcript panel)
  did not update since 18 Nov. Fixed (nothing is sent instead); seen working in the app.
- `Control.tsx` 1,962 → 1,728 lines (live controls in `features/service/LiveControls.tsx`),
  `api.ts` 2,106 → 947 lines (stand-in in `api.mock.ts`).
